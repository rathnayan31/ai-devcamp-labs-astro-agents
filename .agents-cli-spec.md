# Agent Spec

## Overview
Adapt Lab 2's Scale phase to the existing Pixel Astro ADK agent rather than
building a separate synthetic agent. Preserve the completed Build workflow and
deploy it to Google Agent Runtime with Agent Identity, managed Sessions, and
Memory Bank. This repository implements the lab-side Scale work and adapts the
agent to the existing Pixel Astro server contract. The server checkout is
read-only for this lab: do not modify any server source, configuration, tests,
or deployment files.

## Language
`python`

## Example Use Cases
- A user continues the existing chart conversation after the agent process
  restarts, using the same managed session.
- A user explicitly asks the agent to remember a response-style preference;
  that preference is recalled and applied in a separate conversation.
- The existing agent continues to read user-owned chart data through its
  current read-only MCP tools, with the user's authorization checked as before.

## Tools Required
- Existing Pixel Astro MCP tools and skills, unchanged; they remain the source
  of chart data and specialist behavior.
- Agent Runtime managed Sessions, selected from the engine resource injected
  through `APP_URL`, with an in-memory service retained for local development.
- Agent Runtime Memory Bank and ADK `load_memory`, configured for
  `USER_PREFERENCES` only. A preference is saved only after an explicit user
  request, through a constrained preference tool and a canonical memory event.
- Agent Identity for the deployed agent's Google Cloud permissions. It does not
  replace the user's Pixel Astro identity.
- The server authenticates the user's app JWT, mints a short-lived,
  audience-bound read-only Agent MCP token, and supplies it in ADK `state_delta`
  under `user:pixel_astro_token` each turn. The agent forwards that scoped
  token to MCP; it never receives the raw user JWT. The token may remain in
  managed session state until refreshed/expired, but must never enter Memory
  Bank or model instructions.

## Constraints & Safety Rules
- Extend `astro_agent/` only where required for Scale; preserve the existing
  coordinator, specialist routing, tools, skills, and safety policy. The user
  approved Gemini 3.8 Flash after target-project inference tests showed the
  previous Gemini 2.5 models return 404.
- Do not change the MCP tool contract or any file in the Pixel Astro server
  checkout. Adapt only this lab project to the server's existing contract.
- Never store chart/kundali facts, birth details, selected kundali IDs, or
  credentials in Memory Bank. Only explicitly requested response-style
  preferences may be written.
- Do not expose Google credentials or Agent MCP tokens to browser code. Use
  the existing authenticated server chat route, which handles Runtime
  sessions, issues the MCP token, and streams the agent response.
- Keep the previously created `astro_agent_runtime_demo/` prototype and its
  deployed resource untouched; it is not the target of this implementation.
- Deployment to the existing lab Runtime is authorized; do not deploy or alter
  the Pixel Astro server from this lab.

## Success Criteria
- Existing offline safety and agent-wiring tests continue to pass.
- Focused tests verify Runtime selects managed Sessions and Memory Bank from
  the engine resource while local development retains in-memory services.
- Focused tests verify only explicit, allowlisted response-style preferences
  are sent to Memory Bank and that user credentials are not persisted.
- The deployed existing agent uses Agent Identity and managed Sessions in
  `us-central1`; a session resumes across a fresh client/process.
- A response-style preference is recalled in a different session for the same
  user, while chart data and credentials are not recalled from Memory Bank.
- The agent reads the server-minted MCP token from the state key passed in
  `state_delta`; the authenticated server remains the only browser-facing
  integration point.

## Architecture & Sub-Agents
Keep the existing Pixel Astro coordinator, four specialists, MCP tools, skills,
and safety callbacks. Add managed service selection and preference-only memory
to the existing agent; do not replace its real-data workflow with synthetic
fixtures.

## Data Sources & Auth
- Chart data comes only from the existing Pixel Astro read-only MCP tools.
- The trusted app server supplies its short-lived read-only Agent MCP token
  through ADK state on each chat turn. The raw user JWT never reaches the agent.
- Agent Runtime uses Agent Identity for its own Google Cloud access.
- Target: Google Agent Runtime in `us-central1`, using the previously selected
  GCP project `ai-devcamp-lab`.

## Assumptions
- The existing agent project will be enhanced in place if it is not already
  configured for `agents-cli`; no second agent project will be scaffolded.
- The Pixel Astro server already implements the authenticated chat proxy and
  Agent MCP token minting. This lab may inspect that contract but must not
  change the server checkout.
- The existing lab Runtime may be redeployed to deliver this integration.
  Changes to the Pixel Astro server or its production traffic are out of scope.
- Gemini 2.5 Flash, Flash-Lite, and Pro return Vertex AI `404 NOT_FOUND` in
  `ai-devcamp-lab`; a Google Cloud Support case could not be opened because the
  project is not eligible for that support channel. Gemini 3.8 Flash succeeds
  at the `global` endpoint and returns 404 at `us-central1`, so configure
  `GOOGLE_CLOUD_LOCATION=global` for model requests. The existing Runtime has
  been updated to Gemini 3.8 Flash and passed an A2A inference smoke test.
